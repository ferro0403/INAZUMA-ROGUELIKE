A. ROOT CAUSE DEFINITIVA
-----------------------

B1 — roster-full trasformato erroneamente in ineligible

ProfiledSeasonRuntime.acquireOrUpgradeProfile() restituisce quattro risultati
distinti: acquired, upgraded, ineligible e roster-full. Nel target reroll,
recruitPlayer() accetta soltanto acquired/upgraded; ogni altro risultato genera
la stessa eccezione recruit-ineligible. In main, invece, soltanto ineligible
terminava il ramo profile-aware: roster-full proseguiva intenzionalmente verso
la UI comune “Rosa piena — Sostituisci una riserva”.

roster-full non è un errore di persistence e non è ineligible. Deve produrre una
transizione di dominio verso la bench replacement, senza alcun commit preliminare.

B2 — contratto UI one-shot incompatibile con un recruit fallibile

showPlayerOffer(), alla conferma, imposta pickConfirmed=true, disabilita il
bottone e invoca onPick. Non attende un risultato strutturato e non ha reset,
rerender o recovery. Quando recruitPlayer() chiama done(false), il boss callback
non avanza la reward e il modal resta aperto con bottone disabilitato e closure
ormai one-shot.

Trace deterministico:

showPlayerOffer
  -> pickConfirmed=true; button.disabled=true
  -> onPick
  -> recruitPlayer
  -> persistGameplayMutation
  -> acquireOrUpgradeProfile
  -> roster-full
  -> throw recruit-ineligible
  -> rollback
  -> done(false)
  -> nessun advanceBossReward
  -> modal e bottone morti

IE2 Alpine/Shawn e IE3 primo boss usano entrambi season profile-aware, lo stesso
showPlayerOffer(), lo stesso recruitPlayer() e lo stesso callback boss reward.
Sono quindi due manifestazioni dello stesso difetto.

C. FIX DESIGN CONSIGLIATO
-------------------------

1. Introdurre risultati distinti per il recruitment:
   committed-acquired, committed-upgraded, needs-replacement, ineligible,
   persistence-failed, recovery-blocked e cancelled. done(boolean) non è
   sufficiente perché false oggi rappresenta cancel, domain failure e storage
   failure contemporaneamente.

2. Mantenere la prima operazione profile-aware dentro persistGameplayMutation.
   acquired/upgraded seguono il commit normale. ineligible e roster-full devono
   abortire prima di save con sentinel distinti, per esempio
   recruit-ineligible e recruit-roster-full. GameplayPersistence ripristina lo
   snapshot before senza canonical save.

3. Gestire recruit-roster-full come domain transition: dopo il rollback aprire
   la replacement UI sulla run ripristinata, senza done(false), senza toast di
   persistence e senza reward metadata.

4. Dopo la scelta della riserva eseguire un solo commit atomico che:
   - rivalida outgoing player e bench membership su current;
   - rivalida candidato e, se presente, discard instanceId;
   - applica il discard su current;
   - recupera l’equipped item su current;
   - rimuove outgoing da roster/bench/lineup/5v5;
   - chiama acquireOrUpgradeProfile(current, candidate) dopo aver liberato il
     posto e richiede status acquired;
   - completa metadata e bench del nuovo entry;
   - registra PLAYER_RECRUITED una sola volta;
   - enqueue Album una sola volta;
   - aggiorna FiveVFive e smart lineup usando current;
   - applica options.transactionMutate(current, newEntry);
   - salva una sola volta.

5. Non costruire manualmente il profile-aware roster entry. Dopo la rimozione
   dell’outgoing, usare acquireOrUpgradeProfile nello stesso working object. Non
   è recruit prima del replacement: entrambe le mutazioni diventano visibili
   soltanto con il commit finale.

6. onCommitted deve soltanto drenare permanent effects, mostrare toast,
   chiudere/avanzare UI e invocare la continuation. Nessuna mutation canonica e
   nessun nested save devono avvenire in onCommitted.

D. BOSS REWARD ATOMICITY
------------------------

Il commit full-roster finale deve contenere atomicamente:

OLD PLAYER OUT
+ equipped item recuperato / discard applicato
+ NEW PLAYER IN
+ bench, 11v11 e 5v5 consistenti
+ PLAYER_RECRUITED
+ Album outbox
+ BOSS_REWARD_CHOSEN
+ reward pick/excluded metadata

showNextBossReward passa già transactionMutate con
applyBossRewardPickMutation(). La replacement deve riusare la stessa callback.
advanceBossReward può restare una seconda transaction post-commit, purché un
fallimento dell’advance riprenda dalla reward già scelta senza acquisire di
nuovo il giocatore.

Se il commit replacement fallisce, la canonical run deve mantenere outgoing,
equipped item, inventory e reward pending; incoming, actions e Album unlock
devono essere assenti. Il retry deve produrre una sola acquisizione e un solo
reward chosen.

E. EQUIPPED ITEM / INVENTORY FULL
---------------------------------

Con spazio disponibile, il ritorno dell’equipped item deve essere parte dello
stesso mutate(current) della sostituzione.

Con inventory pieno, nessuna mutazione deve avvenire prima della scelta discard.
chooseInventoryDiscard oggi rimuove subito l’item dal run globale: per questo
flow deve poter restituire soltanto l’instanceId scelto. Il commit finale deve
rivalidare e rimuovere quel discard, recuperare l’equipped item e completare la
sostituzione/reward in una singola transaction.

F. UPGRADE / INELIGIBLE
-----------------------

Un upgrade valido non deve aprire replacement. Deve aggiornare il profilo già
posseduto e applicare il boss reward transactionMutate nello stesso commit. Il
reload deve mantenere l’upgrade.

Un vero ineligible non deve avanzare o consumare la reward. Deve mostrare un
messaggio di dominio e ricostruire l’offerta/caller dalla run valida, consentendo
un’altra scelta o skip. Non deve essere confuso con roster-full.

G. NON PROFILE-AWARE
--------------------

La replacement transaction deve essere condivisa, con strategia di acquisizione:

profile-aware: remove outgoing -> acquireOrUpgradeProfile -> assert acquired
legacy:        remove outgoing -> create legacy entry

Inventory, bench, statistics, Album, FiveVFive, smart lineup,
transactionMutate, commit e recovery devono restare comuni. Questo evita di
correggere profile-aware rompendo legacy.

I. FAILURE RECOVERY POLICY
--------------------------

roster-full:
- nessun save;
- passaggio alla replacement UI sulla run rollbackata.

ineligible:
- toast informativo;
- rerender del caller;
- altra scelta/skip.

mutation exception inattesa:
- log e toast;
- rerender; mai riusare la closure precedente.

stale-write:
- GameplayPersistence ricarica canonical read-only;
- render recovery pertinente dalla canonical run.

SecurityError / QuotaExceeded:
- trattare come persistence failure;
- tentare canonical read-only reload;
- rerender recovery se leggibile, recovery/read-only screen altrimenti.

recovery/read-only blocked:
- uscire dal modal stale;
- mostrare recovery screen;
- nessun retry inline finché il guard resta blocked.

Non basta riabilitare il bottone dopo un persistence failure: replaceRun può
aver sostituito l’identità della run, rendendo stale nodo, flow, entry e DOM.

J. GLOBAL RUN VS CURRENT
------------------------

Safe oggi:
- acquireOrUpgradeProfile(current)
- recordRunAction(current)
- enqueueAlbumRecruit(current)
- transactionMutate(current)
- FiveVFive.removeUnavailable(current)
- replaceRun riallinea run e global.run.

Fragile:
- decisione full roster su run.roster prima della transaction;
- benchPlayers derivati dal run globale;
- removedEntry catturato prima della transaction;
- inventory capacity verificata sul run globale;
- flow, node e scoutToken catturati da closure UI.

Bug al boundary transazionale:
- optimizeLineupsForNewPlayer usa sempre run;
- rosterEntry/resolvedRosterPlayer/fiveRole/fiveOverall usano run implicito;
- recruitedOverall dentro mutate usa resolvedRosterPlayer globale;
- chooseInventoryDiscard/removeInventoryItem mutano run prima della transaction;
- special reward finish usa run e save diretti dopo il callback recruit.

Refactor minimo:
- rendere rosterEntry, resolvedRosterPlayer, fiveRoleForPlayerId,
  fiveOverallForPlayerId, effectiveRosterRole e
  optimizeLineupsForNewPlayer parametrizzabili con currentRun=run;
- dentro i boundary transazionali passare sempre current;
- spostare il toast smart-lineup in onCommitted.
