B. REGRESSIONI CONFERMATE
-------------------------

B1. ROSTER PIENO PROFILE-AWARE: SOSTITUZIONE PANCHINA NON PIU' RAGGIUNGIBILE

Aree:
- F — Boss / post-boss
- G — Pull normali
- H — Special match rewards
- N — Stagioni / profiled runtime

Main behavior:
Su main, acquireOrUpgradeProfile poteva restituire acquired, upgraded,
ineligible o roster-full. Il chiamante completava acquired/upgraded, ritornava
solo per ineligible e, per roster-full, proseguiva nel codice comune sottostante
aprendo la UI “Rosa piena — Sostituisci una riserva”.

Reroll behavior:
Su reroll, recruitPlayer accetta esclusivamente upgraded e acquired; qualsiasi
altro stato, compreso roster-full, genera recruit-ineligible. Il runtime
profile-aware continua correttamente a restituire roster-full quando la rosa ha
raggiunto la capacità massima. Poiché l'eccezione viene gestita nello stesso ramo
profile-aware, l'esecuzione non raggiunge più la UI generica di bench replacement.

Evidenza principale:
- js/app.js, recruitPlayer, circa righe 3727-3787;
- js/profiled-season.js, acquireOrUpgradeProfile, circa righe 79-93.

Perché è concreta:
1. IE2/IE3 arriva al primo boss con roster pieno;
2. si sceglie Shawn o un altro candidato nuovo;
3. acquireOrUpgradeProfile restituisce roster-full;
4. reroll lo converte in recruit-ineligible;
5. nessun giocatore viene aggiunto;
6. non si apre la selezione della riserva;
7. il boss reward non avanza.

Rischio: CRITICAL.

Test gap:
Manca un test production-real/browser che attraversi click candidato con roster
pieno -> roster-full -> scelta riserva -> commit combinato recruit+reward ->
callback -> reward successivo -> reload.


B2. DEADLOCK UI DOPO RECLUTAMENTO RIFIUTATO O FALLITO

Aree:
- Q — Error handling / UX deadlock
- impatto su F, G e H

Reroll behavior:
Nel modal dell'offerta, il primo click su conferma imposta pickConfirmed=true,
disabilita immediatamente il pulsante e invoca options.onPick(player).

Se il reclutamento profile-aware fallisce o viene rifiutato:
- viene chiamato done(false);
- non viene eseguito closeModal;
- non viene riaperta l'offerta;
- non viene azzerato pickConfirmed;
- non viene riabilitato il pulsante;
- non è configurato un rerender per recruit-profile.

Nel boss reward il callback avanza solo se completed è true; sul false non viene
eseguita recovery UI. Per recruit-ineligible anche il messaggio d'errore è
soppresso.

Evidenza principale:
- js/app.js, showPlayerOffer, circa righe 3708-3713;
- js/app.js, recruitPlayer, circa righe 3731-3754;
- js/app.js, showNextBossReward, circa righe 5127-5130.

Rischio: CRITICAL.

Questo materializza il pattern:
pickConfirmed=true -> button.disabled=true -> mutation -> failure -> nessun reset,
rerender o retry.


C. AREE SOSPETTE
----------------

C1. MUTAZIONI TRANSAZIONALI CHE USANO ANCORA run E RIFERIMENTI ESTERNI

Rischio: HIGH.

Casi principali:
- cambio ruolo panchina muta run invece del parametro current;
- completamento nodo usa run.currentZone, run.phase e statistiche su run;
- stato match copia ui.match dentro run.activeMatch;
- assegnazione 5v5 muta run dentro la transaction;
- consumabili e statistiche usano helper/global run;
- equip/unequip catturano entry esterne e usano helper che mutano run.inventory.

All'ingresso della transaction current e run sono oggi lo stesso oggetto, quindi
questi casi non sono automaticamente regressioni. Diventano fragili quando un
fallimento provoca replaceRun con un clone/canonico mentre closure DOM, entry e
array restano legati all'oggetto precedente.

Classificazione: suspicious, non regressione provata.
Deep dive: sì, transaction closure ownership.

C2. FAILURE RECOVERY NON UNIFORME FRA LE TRANSACTION

Rischio: HIGH.

Il wrapper supporta onMutationError, onFailure, rerender e onCommitted, ma non
tutti i callsite usano rerender o una recovery route. In particolare:
- recruit non-profile senza roster pieno non ha rerender;
- bench replacement non ha rerender;
- alcune consumable transaction hanno onCommitted vuoto e avanzano la UI dopo il
  ritorno;
- callback esterni possono conservare riferimenti appartenenti allo stato
  pre-rollback.

Classificazione: suspicious. Il problema è provato per recruit-profile; per gli
altri callsite serve fault injection E2E reale.
